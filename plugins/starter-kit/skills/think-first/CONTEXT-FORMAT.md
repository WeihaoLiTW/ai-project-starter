# CONTEXT.md 格式

這份檔案是使用者唯一看得懂、也唯一有資格審查的技術產物。格式要固定，因為
`scripts/check_glossary.py` 會照這個格式去讀 —— 格式錯了，那支腳本什麼都
抓不到，詞彙表就等於沒在把關。

## 語言段落

詞彙表放在一個叫「語言」的第二層標題底下：

```markdown
## 語言

**員工**：
會被排進班表的人。一個人只會是員工或主管，不會同時是兩個。

**主管**：
可以修改所有人班表的人。目前系統裡的第二種身分。
```

規則：

- 標題那一行只能寫 `## 語言`，前後不要加別的字（例如不要寫成
  `## 語言（詞彙表）`），不然腳本認不出這是語言段落。
- 每個詞獨立一行起頭，寫成 `**詞**：`（星號兩個包住詞，接全形或半形冒號）。
  接下來一到兩句話講這個詞在這個專案裡是什麼，不用另起段落，但也可以換行寫。
- 這一行最前面不要加 `-`、數字編號、或任何其他字元，直接以 `**` 開頭。
  `check_glossary.py` 用 `^\*\*` 抓每一行的開頭，前面多一個項目符號，
  那一行就抓不到——腳本不會報錯，只會安靜地少抓一個詞，等於這個詞完全
  沒被檢查過，卻看起來像有格式。
- 一個詞只在這裡定義一次。同一件事不要用兩個詞各定義一次，那正是這份檔案
  要防的問題 —— 每次使用者換講法都會多出一個「新詞」。
- 語言段落在下一個 `##` 開始的地方結束。段落順序不限，但語言段落結束前不要
  插入其他 `##` 標題，否則後面的詞會被腳本判定成不屬於語言段落。

## 為什麼要這樣寫

`check_glossary.py` 會拿測試報告裡出現的詞，跟這裡定義過的詞比對，抓出「測試
報告上有講，但這裡沒定義」的詞 —— 那通常就是使用者換了講法、或是新長出來的
第二個名字。比對靠的是簡單的文字規則，不是猜中文斷詞，所以格式要精確對上：

- 這裡：每個詞開頭必須是 `**詞**：`。
- 測試那邊：docstring 裡提到這些詞，要用「」（直角引號）框起來，例如
  寫成 `"""確認「員工」離職後，他的班表紀錄仍然保留。"""`，不要寫成
  `"""確認員工離職後...`。沒框起來的詞，比對時找不到，等於沒被檢查過。

兩邊對上了，測試報告上每一個業務詞都能回頭查到「這個詞在這個專案裡的定義」，
使用者才能靠這份檔案審查系統是不是真的照他講的意思在做事。

## 什麼時候要更新

使用者講出一個新詞、或者你發現他其實在講同一件事卻用了不同的字，就當場
更新這份檔案 —— 不要等到訪談結束才一次補。發現疑似同義詞時，先跟他確認：
「你剛剛說的『同事』，是我們之前講的『員工』嗎？」確認是同一個東西，就沿用
舊詞，不要多開一條新定義。
