# ADR 格式

ADR（決策紀錄）是寫給**未來的你**，不是寫給使用者審查的 —— 他不會去看這份
檔案，也不需要看。這裡記的是「這個技術決定當時為什麼這樣做」，好讓半年後
有人（可能還是你）想改動這個決定之前，看得到當時的考量，不用重新猜一次。

## 檔名

放在 `docs/adr/NNNN-slug.md`：

- `NNNN`：四位數字，從 `0001` 開始，照建立順序累加，不重複、不跳號。
- `slug`：幾個英文小寫單字，用連字號連接，講這則決定的主題
  （例如 `soft-delete-shifts`、`single-file-database`）。

## 內容：一到三句話

不需要標題分段、不需要 Context / Decision / Consequences 那種正式格式。
一到三句話講清楚三件事：**當時的情況、決定了什麼、為什麼**。

```markdown
# 0001: 員工資料一律保留，不真的刪除

離職員工填過的班表要保留還是刪除，使用者說全部保留。所以「刪除員工」只是
把他標成「離職」，不會真的從資料庫拿掉，班表和誰改過什麼的紀錄都留著。
這樣以後有人問起某天的班表，或者對排班有爭議要回頭查，資料還在。
```

## 「為什麼」要用白話

寫給未來的自己看沒問題，但這份檔案早晚可能被使用者看到、或者被念出來確認，
所以「為什麼」那句話不要用技術理由，要用他能懂的白話：

| 不要這樣寫 | 要這樣寫 |
|---|---|
| To avoid N+1 queries. | 這樣資料變多的時候不會變慢。 |
| To prevent orphaned foreign keys. | 這樣不會因為刪錯東西，害別的紀錄跟著壞掉。 |
| For referential integrity across the audit trail. | 這樣查歷史紀錄的時候，資料對得起來，不會斷掉。 |

判斷標準：唸給沒寫過程式的人聽，他聽得懂結果（會發生什麼事），不用聽懂
機制（為什麼會發生）。

## 什麼時候要寫一則 ADR

只有「難以回頭」的決定才需要：換了會很痛，或者換了會讓使用者之前的資料、
習慣的操作方式跟著變。單純的技術做法選擇（例如用哪個測試框架、檔案怎麼
分）不需要 ADR，也不需要問使用者，直接決定就好。

寫之前**不用**先問使用者要不要留紀錄 —— 決定是你做的，紀錄也是你自己補的，
寫完告訴他「我決定了什麼」就夠了，不是拿紀錄去換他的同意。
