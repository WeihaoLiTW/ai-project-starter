這份在回答什麼

要做一份給非技術新手的 Claude 環境包：貼一段話進他的 Claude，就把行為設定和開發環境一次架好。這份文件回答兩件事 —— 那套環境該由哪些服務組成，以及 kit 本身該怎麼設計。

篩選判準八條。前五條是需求方給的，後三條是研究過程中發現非加不可的：

  1. 容器化：local / staging / prod 跑在同一個 image 上。
  2. 雲上至少兩個環境：staging 和 prod 分開。
  3. 初期每人自己一個帳號，$5/月這一級。
  4. 輕量化：機器不會開大。
  5. 安全要有一定程度。
  6. 非技術者要看得懂：他得能自己點開看到資料，不能只有 SQL 命令列。
  7. Claude 對這個技術夠熟。非技術者沒有能力察覺 Claude 編造了一個不存在的設定。越冷門，編錯機率越高，而使用者連錯在哪都看不出來。
  8. 認證是瀏覽器點一下，不是複製貼上 token。每一道「去後台找 API key 貼過來」都是實際會放棄的地方。

實測結果（2026-08-04）

租了一台真的機器把整條路走過一遍。以下每一項都是實際跑出來的，不是查文件得到的。

Zeabur 的模式已經變了 —— 這是最大的發現

共享叢集全面廢除。 CLI 直接回：

Shared clusters are deprecated.
Please rent a Server and use server-XXXXXXXX as the region code.

所以 Zeabur 不再是「$5/月的共享 PaaS」，而是你自己伺服器的控制台。定價頁那一列的原文是關鍵：「Manageable own servers — Servers you purchased and own elsewhere」。方案費是管理費，不含算力。

真實成本 = 方案費 + 主機租金。 Free 方案 $0 + 主機租金，或 Dev $5 + 主機租金。

不是「Install K3s」，是重裝成 ZeaburOS

我先前查到的官方文件說「點 Install K3s」，已經過時。實際流程是：設定 → 危險區域 → 重裝作業系統 → 選 ZeaburOS。畫面明確警告會清空磁碟。

可選 OS：ZeaburOS（最新版）、Ubuntu 24.04 LTS、Debian（即將推出）、Fedora（即將推出）。說明是「選 ZeaburOS 重裝後直接成為部署節點；選標準發行版則拿回一台標準 VPS」。

重裝耗時約 2 分鐘，完成後 HasK3s 變 true。ZeaburOS 自己回報是 Ubuntu 24.04.4 LTS 基底。

結論：$3 那台 2 GB 的跑不動這個架構。 光 ZeaburOS 加 K3s 就吃 1.5 GB，只剩 0.5 GB 給應用程式。兩個 Django 環境要 300–500 MB，等於零餘裕，部署時的記憶體尖峰必定 OOM —— 而 OOM 對非技術者是完全無法診斷的狀況。4 GB 是下限，不是選配。

Volume 對照實驗 —— 結論與本機 Docker 一致

用兩份 template YAML 建了對照組（不掛 volume）和實驗組（掛 /data），各寫一筆 marker 後重啟容器：

/data 掛載狀態重啟後 marker
對照組（無 volume）無獨立掛載GONE
實驗組（有 volume）/dev/vda2 on /data type ext4PRESENT

證實了資料消失的真正原因：不是「掛載 volume 會清空目錄」，而是沒掛 volume 的期間，寫進去的東西活不過容器重建。對照組根本沒有掛載動作，資料就已經沒了。

而且 template YAML 的 volumes 宣告確實生效 —— 實驗組的 /data 是真的 ext4 掛載點。這代表部署設定（含 volume）可以整份寫在 repo 裡，不必存在某個人的瀏覽器操作記憶裡。

三個結論：

  1. Dev $5 的「購買網域」確定不需要 —— 它賣的是「在 Zeabur 站內買」，而綁自己的網域 Free 就能做。
  2. 預設網址比預期好用：子網域名稱可以自己取，所以能是 某公司-排班.zeabur.app 這種看得懂的名字，不是隨機字串。所以 v1 不碰自訂網域不是將就，是真的夠。
  3. 自訂網域隨時能走，不必提前告知對方「以後要升級」 —— 消掉一個原本擔心的限制。

但有個給非技術者的陷阱：測試時用了一個根本不擁有的網域（probe-check.example.com），Zeabur 照樣接受。它不在建立時驗證所有權，只給 DNS 設定指示。所以打錯字不會當場報錯，要等使用者發現網址連不上才知道。若之後要支援自訂網域，安裝嚮導得自己做一次拼字確認。

如果真要綁自訂網域，最麻煩的不是 Zeabur 這一側

DNS 設定要在買網域的那家公司的後台做，不是在 Zeabur。使用者要在兩個網站之間來回，而 A 記錄、CNAME、TTL 這些詞對他是完全的黑話。前面設計的「技術問題翻譯成業務問題」在這裡幫不上忙，因為這不是取捨，是純粹的操作步驟。

另外 Zeabur 文件明確提到：網域掛在 Cloudflare 後面時不能選 Full (Strict) SSL 模式，否則會連不上。這是典型「兩個服務各自都對、合起來壞掉」的問題，而錯誤畫面看不出原因。

這兩點加起來，是 v1 避開自訂網域的主要理由。

退款是按比例退（先前查不到，現在確認）

申請退款：申請剩餘時間的按比例退款。伺服器將被註銷，退款將記入您的帳戶餘額。

所以短期驗證不會虧整個月。另外自動續約預設是開啟的，不關就會一直續。

付款有兩條路，錯誤訊息只講一半

沒有付款方式時租用會失敗：please bind a credit card or recharge credits first。實際上台灣／中國區使用者常見的路徑是充值（可用支付寶，轉成 Zeabur Credits），不是綁卡 —— 而設定頁上只看得到「充值」。

這一輪就是因為只看到「綁卡」那半而走錯方向。安裝嚮導必須把兩條路都列出來。

CLI 與網頁的能力缺口

要做的事CLI實際只能
安裝 ZeaburOS / K3s沒有指令網頁
掛載 volume沒有指令template YAML（可）或網頁
刪除主機沒有指令網頁
列出 environment沒有指令從網頁 URL 的 ?envID= 撈
租主機、建專案、部署、exec、重啟、看 log都有—

環境 ID 那條特別麻煩：service exec 需要 --env-id，而 context set env 只吃 ID 不吃名稱，但 CLI 沒有任何指令能列出環境。只能開網頁看 URL。

另一個限制：Docker image（PREBUILT）部署的服務不能 in-place redeploy，會回 You must bind a GitHub repository to the service to allow redeploying in-place。正式專案會綁 GitHub 所以不受影響，但探針只能用 service restart。

Cowork 可以被企業政策整個關掉

測試時發現 Roku 的企業帳號在網頁版和桌面版都沒有 Cowork 分頁（側邊只有 Home / Chat 和 Code，展開 More 也沒有）。

這是 spec 的前提條件：如果對方公司之後升到 Team 或 Enterprise，管理員沒開啟的話整套 kit 就用不了。安裝的第一步應該是「確認你看得到 Cowork」，看不到就別往下走 —— 否則對方會走完一半才發現做不下去。

兩個 Cowork 未知數：用設計繞掉，不等驗證

原本列了兩題待驗（Cowork 能不能跑 docker、能不能自動跳 connector 授權）。因為手上沒有可用的 Cowork 帳號，改成讓兩種答案都可接受。

Q1「能不能跑 docker」→ 架構不需要它。

  • 建置在 Zeabur 那邊做 —— 它從 repo 讀 Dockerfile，用自己的建置機器 build，不是在使用者機器上 build
  • 測試只需要 Python —— Django + 記憶體 SQLite，不需要容器

所以 docker 只有 Zeabur 會用到。代價是誠實的：local 不再是「跟 prod 位元級相同的容器」，而是「跑同一份程式碼的 Python 環境」。但真正重要的性質還在 —— staging 和 prod 是同一個 image，local 跑同一份程式碼與同一份相依清單。這個規模夠用，而且換來架構不依賴無法驗證的能力。

Q2「能不能自動跳 connector 授權」→ 照最壞情況寫。

能自動是 3 步，不能是 6 步，兩種都能完成安裝。所以安裝嚮導照「不能自動」寫，明確帶對方一個一個加。若實際可自動，多餘步驟會是無害的空轉（Claude 發現已連上就跳過）。反過來寫才會出事 —— 假設能自動、結果不能，對方會卡在一個沒有指示的畫面。

錯誤訊息品質是實質風險

這一輪撞到三個，都是非技術者會卡死的類型：

  1. 租用失敗只說「綁卡或充值」，沒說在哪裡做，而且兩條路只有一條在設定頁上看得到。
  2. CLI 先印 Server rented successfully，接著才報付款失敗 —— 兩個訊息互相矛盾。
  3. ZeaburOS 沒裝就建專案，只回 An error occurred, please try again later —— 既沒說原因也沒說下一步。這個最危險。

因應方式：安裝嚮導必須把「充值 → 租主機 → 重裝 ZeaburOS → 建專案」寫成硬性順序，而不是等使用者撞到錯誤才發現。

架構怎麼收斂到這裡

第一版是「GitHub + Supabase + Cloudflare + Google」四個帳號。收斂過程值得記，因為每一刀都是被一個具體限制推動的。

  1. 容器化的要求砍掉 Cloudflare。 Workers 跑 V8 isolate，不是容器，本機無法用同一個 image 重現。Vercel、Netlify 同理。
  2. SQLite 砍掉整個「託管資料庫」層。 一旦接受初期用 SQLite，Supabase / Neon / 託管 Postgres 全部不需要。
  3. 一度選了 PocketBase（單一執行檔 = SQLite + auth + admin UI），但它未達 1.0、官方不保證向後相容、主要一人維護、admin 只有英文。
  4. 最後回到 Django。 它一樣是單容器 + SQLite + 內建 admin + 內建 auth，但多了 20 年成熟度、專職 security team、LTS 版本，而且 admin 後台有完整繁體中文。重量從 ~80 MB 變 ~150–250 MB，在這個規模無關痛癢。

安全這條是分水嶺

Django 的安全機制是預設開啟、要主動關掉才會出事：ORM 自動防 SQL injection、模板自動跳脫防 XSS、內建 CSRF token、防點擊劫持 middleware、密碼加鹽 PBKDF2。更重要的是機制面 —— 專職 security team、公開漏洞揭露流程、三年支援的 LTS。

FastAPI 相反：它是 micro-framework，使用者系統、admin 後台、ORM、CSRF、session、密碼 hash 全部要自己接。在「Claude 代寫、使用者無法審查」的情境下，任何一塊漏掉就是洞，而且不會報錯、不會當機，網站看起來完全正常。

對 Python Taiwan 社群回饋的回應

社群普遍認為 Django 難學、「很多設定不知道在做什麼」，建議新手從 Flask/FastAPI 開始。但那串討論的前提是「人要學這個框架」，我們的情境是「Claude 寫、使用者不學」，所以「難學」權重接近零；反而「內建東西很香」「ORM 太香」這兩個優點權重更高。

不過那個風險沒有消失，只是換了形式 —— 從「學習者不懂」變成「Claude 可能設錯，而沒人發現」。經典災難是 DEBUG = True 忘記關就上線，錯誤頁會把設定和檔案路徑露給所有訪客，網站看起來完全正常。

因應：kit 提供設定好的 Django 專案樣板（dev/prod 設定分離、DEBUG 和 SECRET_KEY 從環境變數讀），Claude 不從零建專案；環境健檢驗證這幾項設定。

部署平台：Zeabur

在 $5/月、每人自己一個帳號的前提下，Zeabur 和 Railway 很接近。原本選 Zeabur 的理由只有中文介面，但實測後多了一個更重要的：額度用完是暫停服務、不扣款。

超支保護這一項，Zeabur 的預設值明顯比 Railway 安全。

Zeabur：額度用完 → 服務暫停，資料保留，下期額度重置後恢復。
Railway：額度用完 → 繼續跑並扣款；硬上限是選擇性的、預設關閉、而且最低只能設 $10。

對非技術者，「服務停了」比「收到一張沒預期的帳單」好處理太多 —— 停了他會來問你，扣款可能三個月後才發現。這也讓安裝嚮導少一個強制步驟（不用帶他設花費上限）。

「Claude 對 Zeabur 不熟」這項權重下修過。 如果架構是「平台只當跑 Docker 的地方」，Claude 需要的平台特有知識很窄 —— Dockerfile 和環境變數它超熟，看 log 是在 UI 上點。暴露面比原本假設的小。但這代表 kit 的部署 skill 必須把操作步驟寫死，不能靠 Claude 自己推，而且 Zeabur 改介面時要跟著改。

Kit 設計 · 行為層

核心原則：不要問使用者他答不出來的問題。 非技術者被問「你要用 SQLite 還是 PostgreSQL」只有兩種反應 —— 瞎猜，或去 Google 然後更混亂。兩種都比 Claude 直接決定更糟。

三支柱

一、怎麼講話 —— 繁中、白話、術語第一次出現時用括號補一句人話。

二、怎麼動手 —— 放手模式。讀取、產生新檔、跑分析直接做；只有刪除和對外發布才停下來問。每次動完檔案自動 commit。

三、怎麼決定 —— 見下。

決策規則（三段）

  1. 技術決策底下有業務取捨 → 翻譯成業務問題來問。 不是「不能問」，是「不能用技術的樣子問」。
  2. 底下沒有業務取捨 → Claude 直接決定，寫 ADR。 密碼用什麼演算法存、檔案怎麼命名、要不要加索引。
  3. 業務答案之間的交互後果 → Claude 自己推導並處理，不再回頭問。

還有一條檢查點：如果一個技術決策翻譯不出業務問題，那是信號 —— 代表 Claude 還沒真的想清楚這個決策會影響什麼，該回頭再想，而不是當作「沒有業務取捨」跳過。

翻譯的實例（已驗證）

問使用者的樣子底下的技術決策實測答案
員工離職後，他填過的班表要保留還是消失？soft delete vs hard delete全部保留，只是不能登入 → soft delete
最多多少人同時用？會開放給外部嗎？SQLite vs Postgres幾十人、只有內部 → SQLite 確認夠用
除了員工和主管，還有第三種人嗎？要不要做權限系統就兩種 → Django 內建 is_staff 就夠
排好的班被改了，需要知道是誰改的嗎？要不要做 audit log需要且要能查 → 要做 audit log

這組實測證明了規則的必要性。 三題往簡單走，一題往複雜走 —— 而那個往複雜走的（audit log）正是 Claude 自己絕對會決定省掉的。「內部小工具、幾十人、不對外」，任何合理的技術判斷都會說不用做稽核。但使用者說要，因為他知道排班會有爭議、有爭議就要有依據。這是業務知識，不是技術判斷。

交互後果的實例：要能查「誰改的」+ 離職帳號保留 = audit log 會指向已離職的人，所以那些使用者記錄真的不能刪（刪了 audit log 就變成一堆查不到人的 ID）。這是從兩個業務答案推出的技術後果，Claude 要自己接住，不能再回頭問。

翻譯是有損的。 上表第二題只問了「多少人同時用」，但 SQLite 的限制其實是「同時寫入的人數」，資料總量也是因子。所以 skill 要提醒 Claude：翻譯完之後自問「使用者的答案是否足以支撐這個技術決策」，不夠要補問。

決定了要說，但不要求確認

資料我存在一個叫 SQLite 的檔案裡 —— 就是一個檔案，簡單、備份容易，你們這個規模夠用。哪天人多到跑不動，我會告訴你要換。

使用者有知情權，但不用承擔他判斷不了的決策責任。反面教材是「你要用 SQLite 還是 PostgreSQL？」

寫死的預設（使用者不需要知道，但錯了會出事）

  • 技術棧：Django + SQLite + Zeabur + GitHub
  • Django 專案樣板結構，settings 分 dev / prod
  • DEBUG 一律從環境變數讀，prod 絕不為 true
  • SECRET_KEY 從環境變數讀，不進 git
  • volume 必須在第一次啟動前掛好
  • 花費上限要設

Kit 設計 · 測試

為什麼對非技術者特別重要：他無法察覺「改 A 壞了 B」。 他會在三天後發現某功能不見了，但不知道是哪次改壞的。git 能回溯，前提是他得先知道壞了 —— 測試就是那個機制。

Local 全綠很容易，這是選 Django + SQLite 的意外紅利

測試用記憶體裡的 SQLite，不用起任何服務，零外部依賴。全部測試跑完是幾秒鐘的事，完全離線。如果當初留著 Supabase，測試就得連雲端或起 Docker，迭代速度差一個量級。

韌性上的好處：測試不需要 Docker，只要有 Python。所以就算「Cowork 能不能跑 docker」答案是不行，測試這條路依然成立。

三道保命繩串起來

Claude 改了程式碼
  → 自動跑測試
  → 綠了才 commit
  → 紅了不 commit，直接修到綠

結果是 git 歷史上每一個 commit 都是測試綠的狀態。回溯到任何一點，拿到的都是能跑的版本。這讓「放手模式」真正安全 —— 不是「反正壞了可以回」，是「隨時可以回到一個確定能跑的版本」。

測行為，不測實作

測「員工填了時段之後，主管在後台看得到」，不是「save_shift() 回傳 True」。後者在重構時會壞掉，然後非技術者面對一個他看不懂的紅字。

測試報告變成「系統能力清單」

跑完測試產一張中文 HTML 報告，列出系統保證會做的每件事：

✅ 員工可以填寫自己的可排班時段
✅ 主管在後台看得到所有人填的時段
✅ 同一個人不能重複填同一天
✅ 沒登入的人看不到別人的資料

對非技術者，這張表同時是三件事：系統沒壞的證據、系統會做什麼的清單、跟同事解釋這東西能幹嘛的文件。而且每次改完自動更新。

Local 和 CI 的分工有一條不能破的規則

CI 跑的測試必須是 local 測試的超集，多出來的部分只能是「非得真實部署才驗得了」的東西（部署煙霧測試）。

破了這條就會出現「我這邊都綠的，為什麼 CI 紅了」—— 非技術者遇到這種狀況會直接卡死，因為他無法在本地重現。

Kit 設計 · 想清楚再做

基於 Matt Pocock 的 grill-with-docs（MIT）。它比純 grill-me 多做兩件事：訪談中即時維護 CONTEXT.md 詞彙表，並在遇到難以回頭的決策時寫 ADR。理論根據是 DDD 的 ubiquitous language。

為什麼對非技術者比想像中重要

他的問題不只是想太淺，是講的話沒有固定意義。 今天說「員工」、明天說「同事」、後天說「人員」—— 可能指同一件事，也可能指正職／兼職／外包。Claude 每次照字面理解，系統裡就同時出現 employee、staff、worker 三張表。而他永遠不會發現，因為他看不懂程式碼。

CONTEXT.md 把「員工」定義死一次，之後資料表、介面文字、測試報告全用同一個詞。這是他唯一看得懂、也唯一有資格審查的技術產物。

ADR 則是「技術決策要告知」的落地形式 —— 比口頭講一句好，因為那句話會消失在對話記錄裡，ADR 留在 repo 裡。三個月後想問「當初為什麼用這個」，有地方查。

四項改造（原版是寫給工程師的）

  1. 技術問題翻譯成業務問題再問，不直接 grill 技術決策。這是最重要的改造，跟行為層的決策規則是同一套。
  2. CONTEXT.md 用繁中寫 —— 它是給使用者讀的。
  3. ADR 的「為什麼」用白話 —— 不是「to avoid N+1 queries」，是「這樣資料多的時候不會變慢」。
  4. 語氣改掉 —— 原版的 relentless 對工程師是優點，對非技術者是壓迫感。改成一次一題、每題附建議答案、可以說不知道。

這條線把整個 kit 串起來

使用者講的話 → CONTEXT.md 詞彙表 → 程式碼裡的名字 → 測試報告上的中文

四個地方同一套詞。他在測試報告上看到「員工」，那就真的對應到程式碼裡的 Employee。而且這是可驗證的 —— 可以檢查測試報告上出現的名詞是否都在 CONTEXT.md 有定義。

Kit 設計 · 記憶

Claude Desktop 內建的記憶分好幾層，而且互不相通

層範圍Cowork 能用嗎

最容易踩的誤解：他在 Chat 裡跟 Claude 講過的事，進 Cowork 之後 Claude 不知道。 這要寫進給使用者的說明。

不需要另做 vault，因為 repo 就是記憶

前面設計的三樣東西本質上就是記憶，而且都是檔案、都進 git：CONTEXT.md 詞彙表、docs/adr/ 決策紀錄、folder instructions。

repo 當記憶Obsidian vault
使用者看得到、能改✅✅
有版本、能回溯✅ git 記錄「這條規則什麼時候改的」❌
跟程式碼綁在一起不會漂移✅❌
要另外維護不用要

vault 那套（frontmatter、tags、folder notes、retrieval 規則）是為了跨十幾個 repo 的知識累積。非技術者只有一個專案，那些機制對他是純負擔。

但內建記憶是黑盒子，要補兩條規則

問題情境很具體：Claude 從 project memory 撈到一個過時的結論（三個月前使用者說過「不用做稽核紀錄」，後來改主意但只在對話裡講），Claude 照舊的做，而使用者完全不知道為什麼。這是一個不可見的行為來源。

  1. 重要結論不能只留在記憶裡，必須寫進 repo 的檔案。 記憶可以記「這個人喜歡簡短回答」這種偏好，但凡是會影響系統長相的決定，一律落成 CONTEXT.md 或 ADR。記憶是加速器，不是真相來源。
  2. folder instructions 進 git。 它可以被 Claude 自己更新 —— 好用，但也代表 Claude 可能悄悄改掉規則。進 git 之後自動 commit hook 會記下來，使用者能看到「Claude 在某天改了這條規矩」。

驗法：把 Cowork 的 project memory 清掉，開一個全新 session，Claude 讀 repo 就該能接續工作，不會問「這個之前決定過什麼」。

已知限制與坑（一次列完）

  1. 貼一段 prompt 沒辦法全自動裝好。 裝 plugin、裝 connector、改全域設定都是 UI 動作，Anthropic 刻意鎖在使用者手動同意後面，防的就是有人用一段文字騙你的 Claude 裝東西。能做的是 Claude 一步步帶他點完。
  2. Cowork 的程式碼跑在 Anthropic 遠端，不是對方電腦上。 它只透過桌面 App 讀寫指定資料夾。所以在對方電腦上跑 localhost 服務實質做不到。
  3. 沒掛 volume 之前，寫進去的資料活不過下一次部署。 這是整套架構最危險的坑，而且本機 Docker 已實測確認（見 probes/volume-check/）。原本以為原因是「掛載 volume 會清空目錄」，實測顯示不是 —— 根本沒有掛載動作，資料就已經沒了，因為它們待在容器的臨時層，容器一換就沒。標準 Docker 掛 named volume 的行為其實相反（把 image 內容複製進空 volume）。實務規則不變：volume 必須在第一次啟動前掛好，但講法要改成「沒掛 volume 的期間資料都是暫時的」—— 更準確，也更好對非技術者解釋。
  4. 啟用 volume 後 Zeabur 失去零停機重啟，每次部署斷線幾秒。
  5. Zeabur Dev 每個專案最多 3 個環境（已驗證）。正好對上 local / staging / prod，夠用但沒餘裕 —— 想再加一個 demo 環境就要升級。
  6. SQLite 不能水平擴展，並發寫入有限。 內部工具綽綽有餘，但這是有天花板的選擇。
  7. Django 的 DEBUG = True 上線是經典災難 —— 錯誤頁會把設定和檔案路徑露給所有訪客，網站看起來完全正常。用樣板 + 健檢擋。
  8. Zeabur 的官方定價頁沒寫 runtime 的 CPU/RAM 上限。 它列的 2C4G 是建置時的 CI 規格。第三方資料說 Free 是 1vCPU/2GB、Dev 是 2vCPU/4GB，無官方來源。
  9. Zeabur 沒有遠端 MCP（只有本機 stdio 版，Cowork 裝不了），要走 npx zeabur CLI。
  10. Zeabur 未來多人集中管理很貴：Team $79/月含 3 人，+$24/人。10 人 $247/月。
  11. Google Sheets 官方 connector 只能讀，不能改儲存格、不能加註解、不能把 xlsx 轉成 Sheets。Excel 反而比較順。
  12. Chat 的記憶不會帶進 Cowork。 兩邊是分開的。
  13. 公開 repo 換來無限 CI，代價是任何密鑰外洩就是公開的。
