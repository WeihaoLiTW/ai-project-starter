這份在回答什麼

要做一份給非技術新手的 Claude 環境包：貼一段話進他的 Claude，就把行為設定和開發環境一次架好。這份文件回答兩件事 —— 那套環境該由哪些服務組成，以及 kit 本身該怎麼設計。

篩選判準八條。前五條是需求方給的，後三條是研究過程中發現非加不可的：

  1. 容器化：local / staging / prod 跑在同一個 image 上。
  2. 雲上至少兩個環境：staging 和 prod 分開。
  3. 初期每人自己一個帳號，$5/月這一級。
  4. 輕量化：機器不會開大。
  5. 安全要有一定程度。
  6. 非技術者要看得懂：他得能自己點開看到資料，不能只有 SQL 命令列。
  7. Claude 對這個技術夠熟。非技術者沒有能力察覺 Claude 編造了一個不存在的設定。越冷門，編錯機率越高，而使用者連錯在哪都看不出來。
  8. 認證是瀏覽器點一下，不是複製貼上 token。每一道「去後台找 API key 貼過來」都是實際會放棄的地方。

架構怎麼收斂到這裡

第一版是「GitHub + Supabase + Cloudflare + Google」四個帳號。收斂過程值得記，因為每一刀都是被一個具體限制推動的。

  1. 容器化的要求砍掉 Cloudflare。 Workers 跑 V8 isolate，不是容器，本機無法用同一個 image 重現。Vercel、Netlify 同理。
  2. SQLite 砍掉整個「託管資料庫」層。 一旦接受初期用 SQLite，Supabase / Neon / 託管 Postgres 全部不需要。
  3. 一度選了 PocketBase（單一執行檔 = SQLite + auth + admin UI），但它未達 1.0、官方不保證向後相容、主要一人維護、admin 只有英文。
  4. 最後回到 Django。 它一樣是單容器 + SQLite + 內建 admin + 內建 auth，但多了 20 年成熟度、專職 security team、LTS 版本，而且 admin 後台有完整繁體中文。重量從 ~80 MB 變 ~150–250 MB，在這個規模無關痛癢。

安全這條是分水嶺

Django 的安全機制是預設開啟、要主動關掉才會出事：ORM 自動防 SQL injection、模板自動跳脫防 XSS、內建 CSRF token、防點擊劫持 middleware、密碼加鹽 PBKDF2。更重要的是機制面 —— 專職 security team、公開漏洞揭露流程、三年支援的 LTS。

FastAPI 相反：它是 micro-framework，使用者系統、admin 後台、ORM、CSRF、session、密碼 hash 全部要自己接。在「Claude 代寫、使用者無法審查」的情境下，任何一塊漏掉就是洞，而且不會報錯、不會當機，網站看起來完全正常。

對 Python Taiwan 社群回饋的回應

社群普遍認為 Django 難學、「很多設定不知道在做什麼」，建議新手從 Flask/FastAPI 開始。但那串討論的前提是「人要學這個框架」，我們的情境是「Claude 寫、使用者不學」，所以「難學」權重接近零；反而「內建東西很香」「ORM 太香」這兩個優點權重更高。

不過那個風險沒有消失，只是換了形式 —— 從「學習者不懂」變成「Claude 可能設錯，而沒人發現」。經典災難是 DEBUG = True 忘記關就上線，錯誤頁會把設定和檔案路徑露給所有訪客，網站看起來完全正常。

因應：kit 提供設定好的 Django 專案樣板（dev/prod 設定分離、DEBUG 和 SECRET_KEY 從環境變數讀），Claude 不從零建專案；環境健檢驗證這幾項設定。

決定性的是 5 人上限：10 人在 GitLab 是 $290/月，在 GitHub 公開 repo 是 $0。

GitHub Desktop 這點值得單獨講。 我們選了「放手模式 + git 當保命繩」，那使用者總有一天要自己回溯。GitHub 有滑鼠點得動的桌面工具，GitLab 只能下指令 —— 對非技術者，這是有救和沒救的差別。

Kit 設計 · 行為層

核心原則：不要問使用者他答不出來的問題。 非技術者被問「你要用 SQLite 還是 PostgreSQL」只有兩種反應 —— 瞎猜，或去 Google 然後更混亂。兩種都比 Claude 直接決定更糟。

三支柱

一、怎麼講話 —— 繁中、白話、術語第一次出現時用括號補一句人話。

二、怎麼動手 —— 放手模式。讀取、產生新檔、跑分析直接做；只有刪除和對外發布才停下來問。每次動完檔案自動 commit。

三、怎麼決定 —— 見下。

決策規則（三段）

  1. 技術決策底下有業務取捨 → 翻譯成業務問題來問。 不是「不能問」，是「不能用技術的樣子問」。
  2. 底下沒有業務取捨 → Claude 直接決定，寫 ADR。 密碼用什麼演算法存、檔案怎麼命名、要不要加索引。
  3. 業務答案之間的交互後果 → Claude 自己推導並處理，不再回頭問。

還有一條檢查點：如果一個技術決策翻譯不出業務問題，那是信號 —— 代表 Claude 還沒真的想清楚這個決策會影響什麼，該回頭再想，而不是當作「沒有業務取捨」跳過。

翻譯的實例（已驗證）

問使用者的樣子底下的技術決策實測答案
員工離職後，他填過的班表要保留還是消失？soft delete vs hard delete全部保留，只是不能登入 → soft delete
最多多少人同時用？會開放給外部嗎？SQLite vs Postgres幾十人、只有內部 → SQLite 確認夠用
除了員工和主管，還有第三種人嗎？要不要做權限系統就兩種 → Django 內建 is_staff 就夠
排好的班被改了，需要知道是誰改的嗎？要不要做 audit log需要且要能查 → 要做 audit log

這組實測證明了規則的必要性。 三題往簡單走，一題往複雜走 —— 而那個往複雜走的（audit log）正是 Claude 自己絕對會決定省掉的。「內部小工具、幾十人、不對外」，任何合理的技術判斷都會說不用做稽核。但使用者說要，因為他知道排班會有爭議、有爭議就要有依據。這是業務知識，不是技術判斷。

交互後果的實例：要能查「誰改的」+ 離職帳號保留 = audit log 會指向已離職的人，所以那些使用者記錄真的不能刪（刪了 audit log 就變成一堆查不到人的 ID）。這是從兩個業務答案推出的技術後果，Claude 要自己接住，不能再回頭問。

翻譯是有損的。 上表第二題只問了「多少人同時用」，但 SQLite 的限制其實是「同時寫入的人數」，資料總量也是因子。所以 skill 要提醒 Claude：翻譯完之後自問「使用者的答案是否足以支撐這個技術決策」，不夠要補問。

決定了要說，但不要求確認

資料我存在一個叫 SQLite 的檔案裡 —— 就是一個檔案，簡單、備份容易，你們這個規模夠用。哪天人多到跑不動，我會告訴你要換。

使用者有知情權，但不用承擔他判斷不了的決策責任。反面教材是「你要用 SQLite 還是 PostgreSQL？」

寫死的預設（使用者不需要知道，但錯了會出事）

  • 技術棧：Django + SQLite + Zeabur + GitHub
  • Django 專案樣板結構，settings 分 dev / prod
  • DEBUG 一律從環境變數讀，prod 絕不為 true
  • SECRET_KEY 從環境變數讀，不進 git
  • volume 必須在第一次啟動前掛好
  • 花費上限要設

Kit 設計 · 測試

為什麼對非技術者特別重要：他無法察覺「改 A 壞了 B」。 他會在三天後發現某功能不見了，但不知道是哪次改壞的。git 能回溯，前提是他得先知道壞了 —— 測試就是那個機制。

Local 全綠很容易，這是選 Django + SQLite 的意外紅利

測試用記憶體裡的 SQLite，不用起任何服務，零外部依賴。全部測試跑完是幾秒鐘的事，完全離線。如果當初留著 Supabase，測試就得連雲端或起 Docker，迭代速度差一個量級。

韌性上的好處：測試不需要 Docker，只要有 Python。所以就算「Cowork 能不能跑 docker」答案是不行，測試這條路依然成立。

三道保命繩串起來

Claude 改了程式碼
  → 自動跑測試
  → 綠了才 commit
  → 紅了不 commit，直接修到綠

結果是 git 歷史上每一個 commit 都是測試綠的狀態。回溯到任何一點，拿到的都是能跑的版本。這讓「放手模式」真正安全 —— 不是「反正壞了可以回」，是「隨時可以回到一個確定能跑的版本」。

測行為，不測實作

測「員工填了時段之後，主管在後台看得到」，不是「save_shift() 回傳 True」。後者在重構時會壞掉，然後非技術者面對一個他看不懂的紅字。

測試報告變成「系統能力清單」

跑完測試產一張中文 HTML 報告，列出系統保證會做的每件事：

✅ 員工可以填寫自己的可排班時段
✅ 主管在後台看得到所有人填的時段
✅ 同一個人不能重複填同一天
✅ 沒登入的人看不到別人的資料

對非技術者，這張表同時是三件事：系統沒壞的證據、系統會做什麼的清單、跟同事解釋這東西能幹嘛的文件。而且每次改完自動更新。

Local 和 CI 的分工有一條不能破的規則

CI 跑的測試必須是 local 測試的超集，多出來的部分只能是「非得真實部署才驗得了」的東西（部署煙霧測試）。

破了這條就會出現「我這邊都綠的，為什麼 CI 紅了」—— 非技術者遇到這種狀況會直接卡死，因為他無法在本地重現。

Kit 設計 · 想清楚再做

基於 Matt Pocock 的 grill-with-docs（MIT）。它比純 grill-me 多做兩件事：訪談中即時維護 CONTEXT.md 詞彙表，並在遇到難以回頭的決策時寫 ADR。理論根據是 DDD 的 ubiquitous language。

為什麼對非技術者比想像中重要

他的問題不只是想太淺，是講的話沒有固定意義。 今天說「員工」、明天說「同事」、後天說「人員」—— 可能指同一件事，也可能指正職／兼職／外包。Claude 每次照字面理解，系統裡就同時出現 employee、staff、worker 三張表。而他永遠不會發現，因為他看不懂程式碼。

CONTEXT.md 把「員工」定義死一次，之後資料表、介面文字、測試報告全用同一個詞。這是他唯一看得懂、也唯一有資格審查的技術產物。

ADR 則是「技術決策要告知」的落地形式 —— 比口頭講一句好，因為那句話會消失在對話記錄裡，ADR 留在 repo 裡。三個月後想問「當初為什麼用這個」，有地方查。

四項改造（原版是寫給工程師的）

  1. 技術問題翻譯成業務問題再問，不直接 grill 技術決策。這是最重要的改造，跟行為層的決策規則是同一套。
  2. CONTEXT.md 用繁中寫 —— 它是給使用者讀的。
  3. ADR 的「為什麼」用白話 —— 不是「to avoid N+1 queries」，是「這樣資料多的時候不會變慢」。
  4. 語氣改掉 —— 原版的 relentless 對工程師是優點，對非技術者是壓迫感。改成一次一題、每題附建議答案、可以說不知道。

這條線把整個 kit 串起來

使用者講的話 → CONTEXT.md 詞彙表 → 程式碼裡的名字 → 測試報告上的中文

四個地方同一套詞。他在測試報告上看到「員工」，那就真的對應到程式碼裡的 Employee。而且這是可驗證的 —— 可以檢查測試報告上出現的名詞是否都在 CONTEXT.md 有定義。

Kit 設計 · 記憶

Claude Desktop 內建的記憶分好幾層，而且互不相通

層範圍Cowork 能用嗎
Chat 記憶自動從對話摘要，每 24 小時更新不能 —— 明確不支援 Cowork
Chat Projects 記憶每個 project 各自獨立不能
Cowork Projects 記憶該 project 內的任務之間共用可以
Global instructions所有 Cowork session可以
Folder instructions選定的本機資料夾可以，Claude 能自己更新

最容易踩的誤解：他在 Chat 裡跟 Claude 講過的事，進 Cowork 之後 Claude 不知道。 這要寫進給使用者的說明。

不需要另做 vault，因為 repo 就是記憶

前面設計的三樣東西本質上就是記憶，而且都是檔案、都進 git：CONTEXT.md 詞彙表、docs/adr/ 決策紀錄、folder instructions。

repo 當記憶Obsidian vault
使用者看得到、能改✅✅
有版本、能回溯✅ git 記錄「這條規則什麼時候改的」❌
跟程式碼綁在一起不會漂移✅❌
要另外維護不用要

vault 那套（frontmatter、tags、folder notes、retrieval 規則）是為了跨十幾個 repo 的知識累積。非技術者只有一個專案，那些機制對他是純負擔。

但內建記憶是黑盒子，要補兩條規則

問題情境很具體：Claude 從 project memory 撈到一個過時的結論（三個月前使用者說過「不用做稽核紀錄」，後來改主意但只在對話裡講），Claude 照舊的做，而使用者完全不知道為什麼。這是一個不可見的行為來源。

  1. 重要結論不能只留在記憶裡，必須寫進 repo 的檔案。 記憶可以記「這個人喜歡簡短回答」這種偏好，但凡是會影響系統長相的決定，一律落成 CONTEXT.md 或 ADR。記憶是加速器，不是真相來源。
  2. folder instructions 進 git。 它可以被 Claude 自己更新 —— 好用，但也代表 Claude 可能悄悄改掉規則。進 git 之後自動 commit hook 會記下來，使用者能看到「Claude 在某天改了這條規矩」。

驗法：把 Cowork 的 project memory 清掉，開一個全新 session，Claude 讀 repo 就該能接續工作，不會問「這個之前決定過什麼」。

已知限制與坑（一次列完）

  1. 貼一段 prompt 沒辦法全自動裝好。 裝 plugin、裝 connector、改全域設定都是 UI 動作，Anthropic 刻意鎖在使用者手動同意後面，防的就是有人用一段文字騙你的 Claude 裝東西。能做的是 Claude 一步步帶他點完。
  2. Cowork 的程式碼跑在 Anthropic 遠端，不是對方電腦上。 它只透過桌面 App 讀寫指定資料夾。所以在對方電腦上跑 localhost 服務實質做不到。
  3. 掛載 volume 會清空目錄。 先把服務跑起來、有了資料，之後才想到加 volume —— 那一刻資料全部消失。觸發條件是一個很自然的操作順序，這是整套架構最危險的坑。
  4. 啟用 volume 後 Zeabur 失去零停機重啟，每次部署斷線幾秒。
  5. SQLite 不能水平擴展，並發寫入有限。 內部工具綽綽有餘，但這是有天花板的選擇。
  6. Django 的 DEBUG = True 上線是經典災難 —— 錯誤頁會把設定和檔案路徑露給所有訪客，網站看起來完全正常。用樣板 + 健檢擋。
  7. Zeabur 的官方定價頁沒寫 runtime 的 CPU/RAM 上限。 它列的 2C4G 是建置時的 CI 規格。第三方資料說 Free 是 1vCPU/2GB、Dev 是 2vCPU/4GB，無官方來源。
  8. Zeabur 沒有遠端 MCP（只有本機 stdio 版，Cowork 裝不了），要走 npx zeabur CLI。
  9. Zeabur 未來多人集中管理很貴：Team $79/月含 3 人，+$24/人。10 人 $247/月。
  10. Google Sheets 官方 connector 只能讀，不能改儲存格、不能加註解、不能把 xlsx 轉成 Sheets。Excel 反而比較順。
  11. Chat 的記憶不會帶進 Cowork。 兩邊是分開的。
  12. 公開 repo 換來無限 CI，代價是任何密鑰外洩就是公開的。

試跑清單

A. Zeabur 部署那條路

  1. 「3 own servers」到底是什麼意思？ 我讀成 BYOC 自帶伺服器的數量，不是服務數量上限 —— 但不確定。如果是服務數上限，我們的 4 個服務配置就不夠（staging 和 prod 各一個 app + 一個 volume），架構要調整。這是進去第一件該確認的事。
  2. 從零到 Django 跑起來、能開 /admin，花幾分鐘、卡在哪一步。
  3. 驗證 volume 的順序坑：故意試「先跑起來、寫一筆資料 → 再掛 volume」，確認資料是不是真的被清空。這決定安裝流程裡 volume 那步必須排在哪。
  4. 寫一筆資料 → 觸發重新部署 → 確認那筆資料還在。 這條會直接變成 spec 的核心成功條件。
  5. 部署一次斷線多久；綁自訂網域要幾步。
  6. Dev 方案每服務的 CPU/RAM 上限實際是多少（官方頁沒寫）。

B. 兩個 Cowork 的未知（比選哪家平台更重要）

問題如果是「不行」會怎樣
Cowork 的執行環境能不能跑 docker？local 這層無法容器化，三環境一致只能做到 staging 和 prod 兩層。但測試不受影響（Django + SQLite 只要 Python）
Cowork 能不能加自訂遠端 connector 並自動跳 OAuth？授權要對方自己在 Connectors 頁面一個一個加，安裝流程從 3 步變 6 步

C. 成本與超支保護

  1. Zeabur Dev $5 額度用完是「暫停服務」還是「自動扣款」？ Free 層已知是暫停不扣款，Dev 層無官方確認。如果 Dev 層也是暫停，那對非技術者是比 Railway 更安全的預設值。
  2. 掛 4 個服務跑一週，看燒掉多少額度。
  3. 如果 Zeabur 是「會扣款」，就要找它的花費上限設定在哪，並寫進安裝嚮導的強制步驟。
